# Arcana Diary API

FastAPI-сервис расклада и ИИ-чтеца (этап 4.2), входа, дневника и аккаунта (этап 4.3). Спецификации —
`docs/superpowers/specs/2026-11-14-stage4-2-reader-design.md` (раздел 8 — решения после проверки Fable 5.2) и
`docs/superpowers/specs/2026-11-19-stage4-3-accounts-diary-design.md`; планы —
`docs/superpowers/plans/2026-11-14-stage4-2-reader.md` и `docs/superpowers/plans/2026-11-19-stage4-3-accounts-diary.md`.

## Тесты

```bash
cd ~/arcana-diary/api
.venv/bin/pip install -r requirements-dev.txt
.venv/bin/pytest -q
```

Тесты с базой поднимают временный контейнер `postgres:16.10-alpine` (нужен Docker) и удаляют его в конце; без Docker
они пропускаются с причиной. Свою пустую базу можно задать через `TEST_DATABASE_URL` — тесты очищают её таблицы.
Ни один тест не обращается к Anthropic, Supabase или Cloudflare: поставщик модели — `FakeProvider`, Turnstile — подделка,
токены входа подписываются тестовым ключом ES256, а ключи подставляются вместо сети (`helpers.FakeJwks`).
`TEST_DATABASE_URL`, похожий на Supabase (`supabase.co`, `pooler.supabase.com`), тесты не трогают — выход с кодом 4,
если не задано `TEST_DATABASE_ALLOW_SUPABASE=yes`.

## Запуск без ключей

```bash
docker run -d --rm --name arcana-dev-pg -e POSTGRES_PASSWORD=dev -p 127.0.0.1:55432:5432 postgres:16.10-alpine
cd ~/arcana-diary/api
READER_PROVIDER=fake DATABASE_URL=postgresql://postgres:dev@127.0.0.1:55432/postgres .venv/bin/uvicorn app.main:app --reload
```

Миграции из `api/migrations/` применяются при старте (если база недоступна — повтор каждые 30 секунд, запросы до
этого получают `503`). `READER_PROVIDER=fake` отвечает заготовленным текстом без вызова модели.

## Переменные окружения

Секреты — только в `deploy/.env` на сервере, в репозиторий не попадают (шаблон — `deploy/.env.example`).

| Переменная | По умолчанию | Что это |
|---|---|---|
| `DATABASE_URL` | пусто | строка подключения Postgres (Supabase: пулер в режиме transaction); пусто — `503` на всё, кроме `/health` |
| `ANTHROPIC_API_KEY` | пусто | ключ Claude API; нужен и при `READER_PROVIDER=openai` или `gemini`: проверка вопроса всегда на Claude |
| `OPENAI_API_KEY` | пусто | ключ OpenAI; обязателен при `READER_PROVIDER=openai` |
| `GOOGLE_AI_API_KEY` | пусто | ключ Google AI (Gemini); обязателен при `READER_PROVIDER=gemini` |
| `READER_PROVIDER` | `claude` | `claude`, `openai`, `gemini` или `fake`; `READER_MODEL` должна быть моделью этого поставщика |
| `READER_MODEL` | `claude-haiku-5-5` | модель чтеца, уточнений и карты дня |
| `READER_EFFORT` | `medium` | `output_config.effort` чтеца (`low` … `max`); сравнить уровни на тестовом наборе |
| `GUARD_MODEL` | `claude-haiku-5-5` | модель проверки вопроса (effort `low`) |
| `JUDGE_MODEL` | `claude-sonnet-5-5` | модель-судья, только для `api/evals` |
| `TURNSTILE_SITEKEY`, `TURNSTILE_SECRET` | пусто | ключи Cloudflare Turnstile; без секрета запрос после порога получает `403` |
| `TRUST_CLOUDFLARE` | `false` | ровно `true` или `false`; `true` — только когда прокси Cloudflare включён: Caddy пускает лишь адреса Cloudflare, API читает `CF-Connecting-IP` и `CF-IPCountry` (см. ниже) |
| `DAILY_BUDGET_USD` | `5` | суточный предел расходов на модель по `llm_calls`; сверх — значения карт из базы (проверка вопроса работает дальше) |
| `GUARD_BUDGET_USD` | `1` | суточный предел расходов на проверку вопроса моделью; сверх — только стоп-фразы, остальные вопросы получают `503 {"reason": "unavailable"}` |
| `FIRST_TOKEN_TIMEOUT_S` | `15` | сколько ждать первых слов чтеца до запасного ответа |
| `GUARD_TIMEOUT_S` | `5` | тайм-аут проверки вопроса (решение владельца 19.11.2026, спецификация §10.10) |
| `CLEANUP_INTERVAL_S` | `3600` | как часто удалять просроченное (гостевые расклады, токены переноса) и возвращать слоты за оборванные платные уточнения |
| `SUPABASE_URL` | пусто | открытый адрес проекта Supabase (`https://<ref>.supabase.co`, не секрет); пусто — вход выключен, любой `Authorization: Bearer` получает `401` |
| `SUPABASE_ANON_KEY` | пусто | открытый ключ проекта Supabase (anon / publishable, не секрет) для входа в браузере; вместе с `SUPABASE_URL` включает вход на сайте (`GET /api/auth-config`), без него кнопки «Save to diary» нет. Никогда не `service_role` / `sb_secret_…`: такой ключ API не отдаёт (вход выключен, строка `SUPABASE_ANON_KEY is not the public key` в журнале) |
| `GOOGLE_SIGNIN` | пусто | `true` — на сайте видна кнопка «Continue with Google» (после шага 1 «Вход через Supabase»); пусто или что угодно другое — выключено (другое значение — строка в журнале, API работает) |
| `DAILY_JOB_INTERVAL_S` | `3600` | как часто задача карты дня дописывает недостающие тексты; `0` — выключить |
| `RUN_MIGRATIONS` | `true` | применять миграции при старте |
| `CONTENT_DIR`, `BANNED_TERMS_PATH`, `MIGRATIONS_DIR` | пути в репозитории | в образе заданы в `api/Dockerfile` |

## Адреса

`POST /api/readings`, `GET /api/readings/{id}`, `GET /api/readings/{id}/stream` (SSE), `POST /api/readings/{id}/retry`
(SSE), `POST /api/readings/{id}/followups` (SSE), `GET /api/daily?lang=&tz=`, `GET /api/limits?tz=`, `POST /api/events`
(этап 4.4а, ниже), `GET /api/auth-config` (этап 4.4б: `{"enabled", "supabase_url", "anon_key", "google"}` — открытые
настройки входа для браузера; без `SUPABASE_URL` или `SUPABASE_ANON_KEY` — `enabled: false` и пустые строки). Поддомен `api.`
отдаёт только `GET /health`, остальное — `404`. События потока: `meta`, `section`, `text`, `replace`, `fallback`,
`crisis`, `done`, `error`. Все ответы `/api/*`: `Cache-Control: no-store`, `Referrer-Policy: no-referrer`,
`X-Robots-Tag: noindex, nofollow`. Уточнения: два бесплатных к каждому раскладу (обрезанное или заменённое из базы не
считается); каждое следующее тратит один расклад из дневного лимита (гость — 2, вошедший — 3) и только с `"use_reading": true` в запросе — без него
`402 {"reason": "confirm", "remaining": N}`, раскладов не осталось — `402 {"reason": "plus", "remaining": 0}`. Платное
уточнение, которое не удалось (обрыв, замена из базы, по словарю, без ответа), возвращает расклад; кризисный ответ
проверки вопроса расклад не тратит, метка чтеца `[[crisis]]` — тратит; `done` платного уточнения несёт `used_reading`.
Не больше 8 попыток на расклад (кризисный ответ проверки попытку не тратит, этап 4.5) и 40 запросов уточнений в сутки
с адреса — `429 {"reason": "attempts"}` / `{"reason": "ip_limit"}`. Сверх
`GUARD_BUDGET_USD` вопрос, которому нужна модель, — `503 {"reason": "unavailable"}` (попытка не тратится). Проверок
вопроса моделью при создании расклада — не больше 60 в сутки с адреса, кризисные ответы тоже считаются и вместе с
раскладами ведут к Turnstile с 20-й; сверх 60 — только стоп-фразы, остальное — `503 {"reason": "unavailable"}`.
Любой `422` — `{"reason": "invalid", "fields": [...]}`.

**Этап 4.3.** Вошедший шлёт `Authorization: Bearer <access token Supabase>`; без заголовка (или с `Basic` пароля
стенда) — гость, как раньше. Токен проверяется на каждом адресе `/api/*` до разбора запроса (и на
`GET /api/daily`). Неверный или просроченный токен — `401 {"reason": "auth"}`, ключи Supabase
недоступны — `503 {"reason": "auth_unavailable"}`, адрес только для вошедших без токена — `401 {"reason": "sign_in"}`.
Лимит (этап 4.4б, решения владельца 22.11.2026): гость — 2 расклада в день на устройство, вошедший — 3 на аккаунт на всех устройствах (`GET /api/limits`
отвечает по аккаунту); платное уточнение берёт слот у владельца расклада. Расклад в аккаунте принадлежит только
аккаунту, гостевой — устройству (кука `ad_guest`); владельцу `GET /api/readings/{id}` отдаёт ещё `in_diary`,
`outcome`, `note`. Перенос:
`POST /api/readings/{id}/claim-token` (только устройство, где сделан расклад; `201 {"token", "expires_at"}`, 7 дней, не больше
5 живых на расклад) и `POST /api/account/claim {"tokens": [...], "device": true | false}` → `{"claimed": [id, ...]}` (этап 4.4б, решение
владельца 12: `"device": false` — переносятся только расклады токенов, гостевые расклады устройства остаются; без
поля — `true`, как в 4.3). Дневник:
`GET /api/diary?before=&limit=` (20, не больше 50; `next_before` — начало следующей страницы; этап 4.4б: только 10
последних раскладов — `FREE_DIARY_VISIBLE`, за ними `next_before: null`, и `hidden_count` — сколько более старых
скрыто; выгрузка и `GET /api/readings/{id}` их по-прежнему отдают, владельцу — ещё и `created_at`),
`PATCH /api/diary/{id} {"outcome": "yes" | "partly" | "no" | null, "note": "…" | null}` (заметка до 1000 знаков,
хранится как есть, отдаётся только в JSON), `DELETE /api/diary/{id}` → `204`; чужой расклад — `404`. Аккаунт:
`GET /api/account?tz=`, `PATCH /api/account {"reminders_consent": bool}`, `GET /api/account/export` (файл JSON),
`DELETE /api/account {"confirm": "DELETE"}` — сразу; журналы `llm_calls` остаются. Удаление, создание расклада,
перенос, согласие и список Plus одного аккаунта идут по очереди (блокировка аккаунта в базе); повторный
`DELETE /api/account` с тем же токеном — `401 {"reason": "auth"}`, как и любая запись по токену удалённого аккаунта
(8 дней). Список Plus:
`POST /api/plus/waitlist {"email", "lang"}` — повтор без ошибки, не больше 5 заявок с адреса в сутки; вошедшему
почта берётся только из токена (в токене нет почты — `422`, почта из тела не используется). Память чтеца:
вошедшему в ввод чтеца и его уточнений добавляется `<history>` — до 5 прошлых раскладов той же темы только с
обычными вопросами (группа `ok` от настоящей проверки — `readings.guard_source` `model`/`terms`, миграция 003; вопрос,
не проверенный из-за таймаута или ошибки, не возвращается; дата, вопрос, заголовок; без заметок и отметок), промпты `reader.*.v5`,
`followup.*.v5`.

**Этап 4.5** (спецификация `docs/superpowers/specs/2026-11-20-stage4-5-prelaunch-design.md`). *Сначала помощь, потом
лимит:* `POST /api/readings` — предел адреса и Turnstile, затем проверка вопроса (кризис — `200`, `remaining` как
было, слот не берётся), и только потом `429 {"reason": "limit"}`; уточнение — слот адреса (40 в сутки), проверка
вопроса (кризис — `200`, попытка не берётся), затем `429 attempts`, `402 confirm` / `402 plus`. Человек у лимита
тратит проверку моделью на каждый отказ; это ограничено 60 проверками (расклад) и 40 запросами (уточнение) с адреса
в сутки и `GUARD_BUDGET_USD`; у исчерпанного лимита вопрос, который некому проверить (сверх бюджета или 60
проверок), — `429 limit`, не `503`. До проверки вопроса уточнения по-прежнему отвечают `409 busy` / `no_answer` /
`fallback` (сайт такого не шлёт). *«Да/нет» на три карты:* `{"kind": "yes_no", "count": 3}` (`count` — 1 или 3, по
умолчанию 1; у других видов — `422 {"fields": ["count"]}`) — один расклад, три карты с позицией `card`; у каждой
карты расклада с вердиктом — её голос `vote` (`yes` / `no` / `unclear`, перевёрнутая — `unclear`), `verdict` — по
правилу `decisive_majority` (`content/cards/yes-no-rules.json`, версия 2, решение владельца 21.11.2026): карты
`unclear` воздерживаются, «да» больше «нет» — `yes`, наоборот — `no`, ничья или ни одной — `unclear`; без вердикта
(§8.1) — без голосов. Промпты `reader.*.v6` (раздел на
карту с её голосом, `synthesis` — что склонило итог). *Один запрос — один расклад:* необязательный `request_id`
(UUID) в теле `POST /api/readings` и уточнения (миграция 005). Повтор с тем же номером у того же владельца (аккаунт,
иначе устройство) — тот же расклад (`201`, тот же вид, `remaining` на сейчас), ничего не тратится и не проверяется
заново; у чужого владельца номер ничего не находит. Тот же номер уточнения в этом раскладе — поток этого уточнения
(`meta` с `"replay": true`; сохранённый ответ — `text` или `replace` с `"reason": "saved"` и `done`; ещё пишется —
`error {"reason": "in_progress"}`, сайт читает ответ через `GET /api/readings/{id}`). Номер уточнения `n` — счётчик
попыток расклада, он не повторяется; одновременно пишется одно уточнение на расклад (`409 busy`), и бесплатное
оно или платное, решается по списку, прочитанному под блокировкой расклада. Номер повтора, совпавший с истёкшим, но
ещё не удалённым раскладом, — `409 {"reason": "request_id"}`; при переносе гостевого расклада в аккаунт его номер
стирается. Сайт повторяет запрос, на который не пришло никакого ответа, один раз через секунду (создание расклада
ждёт до 30 с, так что до сообщения «нет сети» проходит до минуты); `502` / `504` — ответ, их сайт не повторяет, и
следующее нажатие с новым номером может дать второй расклад. Платное уточнение, которое чтец закрыл `[[crisis]]`,
расклад оставляет (§9.5), а строка уточнения остаётся как «надгробие» (`answer = {"crisis": true}`, не считается,
текст вопроса не хранится): повтор с тем же номером получает помощь (`crisis`) заново, без вызова модели и без новой
траты; `GET` надгробие не показывает, в выгрузку и в счёт уточнений дневника оно не входит. Часовая очистка удаляет
надгробия старше суток (номер уточнения `n` — счётчик попыток, он от этого не меняется). Кнопка «Попробовать ещё
раз» на потерянном уточнении шлёт тот же запрос с тем же `request_id` и тем же телом (новый номер и другой
`use_reading` — никогда), поэтому доходит и до надгробия.

**Этап 4.6** (спецификация `docs/superpowers/specs/2026-11-22-stage4-6-reader-v7-design.md`). Промпты `reader.*.v7`,
`followup.*.v7`: в обычных вопросах (группа `ok`) чтец смелее говорит о будущем в жизни самого человека, но без дат
и сроков, гарантий и судьбы, чужих чувств и поступков, здоровья, смерти, беременности, суда, выигрыша; в группах без
исхода — ни намёка на исход; при трёх картах заголовок говорит о картах во множественном числе. Испанский: ориентация
карты — «al derecho» / «al revés» (ввод чтеца, строки страховки, сайт); формы рода о читателе запрещены с примерами.
Словарь `reader_banned_terms.json`: фразы о будущем самого человека («will happen», «llegará alguien») убраны из
`en` / `es` и перенесены в `en_redirect` / `es_redirect` — они действуют в группах без исхода (для уточнения — по
более строгой из групп расклада и уточнения) и в карте дня (`check.live_terms`).
Карта дня ES — `daily.es.v5`; судья `judge.v5` (с этапа 4.8 — `judge.v6`).

**Этап 4.7** (спецификация `docs/superpowers/specs/2026-11-22-stage4-7-es-gender-design.md`). После потока каждый
испанский раздел, который остался текстом модели (не строкой из базы карт, подставленной `finalize`), проверяется на
формы рода о читателе (`app/reader/gender.py`: только с привязкой ко второму лицу — «estás/eres/te sientes/sentirte/
estar… + прилагательное или причастие», «a ti mismo», «contigo misma», дублеты «-a o -o», «-o/a»; род карт, вещей и
других людей не считается). Раздел с находкой переписывается одним коротким вызовом модели чтеца
(`app/reader/rewrite.py`: `complete_json`, таймаут `REWRITE_TIMEOUT_S` = 5 с — это предел httpx на каждую фазу
(соединение, затем чтение), так что худшее ожидание перед `done` около 10 с, а первый вызов после выкладки медленнее
(схема JSON компилируется); без повторов, `max_tokens` ≈ 2 раздела + 512, не меньше 1024; разделы — параллельно;
в запросе — абзац и найденные формы); вызов пишется в `llm_calls` с `purpose = 'rewrite'` (миграция 006) и входит в
`DAILY_BUDGET_USD`, сверх бюджета переписи нет. Новый текст берётся, только если он не пустой и изменён, без рода, без фраз
словаря (с учётом группы), с теми же словами вердикта, что и было (не добавлен, не убран, не перевёрнут, не
смягчён), это тот же абзац (сходство по словам не ниже 0,5, у коротких — 0,4; без разметки `< > * #`, переносов строк
и HTML-сущностей, без новых чисел, без вступления «Aquí está…», не по-английски) и в пределах ±30 % слов; иначе (и
при любой ошибке вызова или самого шага переписи) остаётся написанное. Принятая перепись сохраняется и приходит событием `replace` со всеми разделами (`reason`
`gender`, или прежняя причина, если `finalize` уже заменил раздел); уточнение — `replace {"followup": …}` с
`reason: "gender"`, затем `done` с `answer_shown: "model"`; карта дня переписывается до записи в кэш. Английский не
проверяется. Сайт не менялся: он и так заменяет разделы по `replace`. `evals/run.py` делает ту же перепись (вызовы
считаются как `rewrite`) и пишет `gender` / `rewritten` в результат; судья по-прежнему оценивает сырой ответ.
Проверка после выкладки: `SELECT stop_reason, count(*), avg(ms_total), sum(cost_usd) FROM llm_calls WHERE purpose =
'rewrite' GROUP BY 1;` — большая доля `timeout` или `max_tokens` значит поднять `REWRITE_TIMEOUT_S` или потолок;
строка журнала `gender rewrite of <раздел>: taken | original kept` даёт долю принятых. Перед выкладкой миграции 006:
`SELECT conname FROM pg_constraint WHERE conrelid = 'llm_calls'::regclass AND contype = 'c';` — ожидается
`llm_calls_purpose_check`.

**Этап 4.8** (спецификация `docs/superpowers/specs/2026-11-24-stage4-8-reader-meaning-design.md`, решения владельца

## Ограничения, о которых надо помнить

- **Один процесс uvicorn** (`--workers 1` в `api/Dockerfile`): соль адреса и счётчики всплеска живут в памяти; каждый
  деплой обнуляет счётчик всплеска и меняет соль (счёт по адресу за день начинается заново).
- Маршруты синхронные и работают в пуле потоков Starlette (40 потоков): около 40 одновременных генераций, дальше —
  очередь, включая `/health`. Генерация идёт в своей нити и дописывается, даже если человек закрыл страницу.
- Новое соединение с базой на каждую операцию (3–4 на запрос); пул соединений — когда будет видна нагрузка.
- День гостя — по поясу из браузера: меняя `tz`, один гость может получить расклады «за три дня» сразу (до 6). Это
  допустимо; жёсткий предел — 60 раскладов в сутки с адреса и бюджет `DAILY_BUDGET_USD`.
- Уточнение без `tz` считает день по UTC: сайт должен передавать тот же `tz`, что и при создании расклада. Это то же известное
  ограничение, что и при смене часового пояса.
- Вызов модели, прерванный до отчёта о токенах (тайм-аут, обрыв после текста), пишется в `llm_calls` с верхней
  оценкой цены: `max_tokens` по цене выхода (чтец около $0.002, проверка вопроса около $0.0005) — потолок ошибается в
  безопасную сторону. Ошибка до первого текста (нет соединения, неверный ключ, `429` поставщика) пишется без цены.
- Любой UUID в cookie — «вернувшийся гость»: `GET /api/daily` пишет строку `daily_draws` для каждого нового номера (до
  30 запросов в минуту с адреса), у `GET /api/readings/{id}` и `GET /api/limits` своего предела частоты нет. До запуска
  этого достаточно; после включения прокси — правило ограничения частоты для `/api/*` в Cloudflare.
- Карта дня: первый старт пишет 936 текстов (около $0.30), сначала сегодняшние, потом завтрашние и вчерашние; в первые
  10–20 минут после первого старта `GET /api/daily` может отдавать `"source": "fallback"`. После 5 неудачных вызовов
  подряд (пустой ключ, кончился баланс) задача останавливается до следующего часа.
- Токен доступа Supabase действует до своего `exp` (по умолчанию час), в том числе после удаления аккаунта: сайт
  выходит из аккаунта сразу после `DELETE /api/account`, а API отказывает такому токену (см. ниже).
- Страницы дневника идут по времени создания (`before`): два расклада одного аккаунта с одинаковым до микросекунды
  временем на границе страницы могут разойтись по страницам или пропасть из выдачи.
- Токен аккаунта, удалённого меньше 8 дней назад, получает `401 {"reason": "auth"}` на любую запись (таблица
  `deleted_accounts`); через 8 дней запись о нём стирается — дольше любой срок токена Supabase не бывает.
- Реальный потолок на человека — 2 расклада гостем и 3 вошедшим, то есть 5 в день; новые адреса почты (в том числе
  с `+`) дают новые аккаунты. Ограничивают это, как и смену куки гостем, только предел адреса (60 в сутки, Turnstile
  с 20-го) и суточные бюджеты.

## Перед включением `TRUST_CLOUDFLARE=true`

Флаг включает две вещи сразу: Caddy закрывает соединение с любого адреса вне диапазонов Cloudflare
(`deploy/caddy/cf-true.caddy`, до пароля, сайта и API; на порту 80 фильтра нет — там только перенаправление на HTTPS),
а API берёт адрес клиента из `CF-Connecting-IP` и страну для
контактов помощи из `CF-IPCountry`. Правила `ufw` здесь не помогают: порты 80 и 443 публикует Docker, и его правила
идут в обход цепочек `ufw`. Пока флаг `false`, оба заголовка не читаются: адрес — из соединения (Caddy пишет его в
`X-Real-IP`), контакты — по часовому поясу и языку. Значение — ровно `true` или `false`: API с другим значением не
стартует, Caddy не находит файл `cf-<значение>.caddy`. Если у домена появится запись AAAA, а в Docker не включён IPv6,
соединения Cloudflare по IPv6 придут с адреса моста Docker и будут сброшены: AAAA не добавлять, пока IPv6 в Docker
не включён.

1. Сверить диапазоны в `deploy/caddy/cf-true.caddy` со страницей https://www.cloudflare.com/ips/ на день включения;
   при расхождении поправить файл и закоммитить.
2. За один заход: включить прокси (оранжевое облако) для `arcanadiary.com`, `www` и `api`, SSL/TLS — Full (strict),
   затем `TRUST_CLOUDFLARE=true` в `deploy/.env` и `deploy/deploy.sh`. Между этими действиями все посетители
   приходят с адресов Cloudflare и делят один счётчик адреса (60 раскладов в сутки) — не растягивать.
3. Проверить с любой машины: `curl -sS --max-time 10 --resolve arcanadiary.com:443:<IP сервера> https://arcanadiary.com/`
   — ошибка curl (`Empty reply from server` или `HTTP/2 stream 1 was not closed cleanly`), HTTP-ответа нет; через
   Cloudflare `curl -sS -o /dev/null -w '%{http_code}\n' https://arcanadiary.com/` — `401` до запуска, `200` после.
4. Сертификат: Caddy продлевает его у Let's Encrypt проверкой HTTP-01 на порту 80, а там фильтра нет (только
   перенаправление на HTTPS и ответ на проверку). Через сутки после включения и за 30 дней до конца срока сертификата проверить
   `docker compose logs caddy | grep -iE 'obtain|renew|error'`; если продление не проходит — на время продления
   выключить прокси (серое облако) и вернуть `TRUST_CLOUDFLARE=false`, затем включить обратно по шагу 2.

## Вход через Supabase (этап 4.3): шаги владельца

Сервер не хранит паролей и не шлёт писем входа: браузер (экраны 4.4) входит через Supabase JS, API только проверяет
токен (ES256 по ключам `<SUPABASE_URL>/auth/v1/.well-known/jwks.json`, кэш 10 минут).

1. **Google.** Google Cloud Console → APIs & Services → OAuth consent screen: тип External, название Arcana Diary,
   почта поддержки, домен `arcanadiary.com`, области `openid`, `email`, `profile`. Затем Credentials → Create
   credentials → OAuth client ID → Web application: Authorized JavaScript origins — `https://arcanadiary.com`,
   Authorized redirect URIs — `https://<ref>.supabase.co/auth/v1/callback` (точный адрес показан в Supabase на
   странице провайдера). Client ID и Client secret — в Supabase → Authentication → Providers → Google, включить.
2. **Адреса возврата.** Supabase → Authentication → URL Configuration: Site URL — `https://arcanadiary.com`;
   Redirect URLs — `https://arcanadiary.com/diary` и `https://arcanadiary.com/es/diario` (адреса с `?claim=…` им
   соответствуют).
3. **`SUPABASE_URL`** в `deploy/.env` — Project Settings → API → Project URL (не секрет), затем `deploy/deploy.sh`.
   Тот же деплой включает куку стенда (решение владельца 19.11.2026): пока `LAUNCHED=false`, страница, открытая
   с паролем, ставит куку `ad_stage` (HttpOnly, Secure, SameSite=Lax, 7 дней, секрет — в `stage_auth.caddy`, новый
   при каждом деплое), и с ней запросы к `/api/*` проходят без Basic — так вошедший шлёт `Authorization: Bearer`.
   Без пароля стенд по-прежнему закрыт; `deploy/check-indexing.sh` проверяет это после деплоя, а
   `deploy/test-stage-auth.sh` — до него, на временном контейнере. После деплоя каждая вкладка один раз снова
   просит пароль (новый секрет). С `LAUNCHED=true` куки нет.
   Изменение `Caddyfile` пересоздаёт контейнер Caddy (несколько секунд простоя); деплой запускает владелец, не субагент.
   Если первый деплой упал на проверке куки стенда — запустить `deploy/deploy.sh` ещё раз (в этом деплое ещё работает старый `deploy.sh`).
   Откат этого коммита требует после `git revert` выполнить `cd deploy && docker compose up -d --force-recreate caddy`: откатанный `deploy.sh` Caddy уже не пересоздаёт, а старый одиночный mount `Caddyfile` импортировал бы удалённый файл.
4. **До запуска** — почтовый сервис для писем входа (Authentication → SMTP Settings); встроенная почта Supabase —
   только для проверки, несколько писем в час.
5. **Настройки, на которые опирается API** (Authentication → Sign In / Providers и Settings): анонимный вход
   выключен (API всё равно отвечает `401` на токен с `is_anonymous`), «Confirm email» включено (иначе в токене
   может оказаться чужая неподтверждённая почта), срок токена (JWT expiry) — 3600 секунд.
6. **Перед первым развёртыванием 4.3** — в SQL Editor:
   `select to_regclass('public.profiles'), to_regclass('public.claim_tokens'), to_regclass('public.plus_waitlist'), to_regclass('public.deleted_accounts');`
   — все четыре `NULL`. Если какая-то таблица уже есть (`profiles` бывает в шаблонах Supabase), миграция 002 будет
   повторяться каждые 30 секунд: сначала переименовать или удалить ту таблицу.
7. Удаление аккаунта стирает и пользователя Supabase (`DELETE FROM auth.users` через `DATABASE_URL`). До того как
   открыть вход кому-либо, проверить в SQL Editor: `select has_table_privilege(current_user, 'auth.users', 'delete');`
   — `true`. Если пользователь Supabase не удалился, в журнале API будет строка уровня `ERROR` с номером аккаунта
   («Supabase user was not deleted») — удалить его вручную в Authentication → Users.

## Передача в 4.4 (экраны)

- Заметки, вопросы, заголовки и всё из выгрузки — сырой текст: выводить через `textContent`, никогда через
  `innerHTML` или `set:html`.
- Поток расклада и уточнений читать через `fetch` с заголовком `Authorization`: `EventSource` не умеет слать
  заголовки.
- На `401 {"reason": "auth"}` — один раз обновить токен и повторить; не помогло — выйти из сессии и повторить как
  гость. `401 {"reason": "sign_in"}` — показать вход.
- 401 без JSON-причины на стенде — перезагрузить страницу (кука стенда устарела), не обновлять токен.
- Сразу после `DELETE /api/account` выйти из сессии Supabase на этом устройстве.
- `next_before` передавать в адресе закодированным (`+00:00` → `%2B00%3A00`, `URLSearchParams` делает это сам).
- После `POST /api/account/claim` убрать `?claim=…` из адресной строки (`history.replaceState`).
- Расклад в аккаунте принадлежит только аккаунту: после выхода из аккаунта это устройство видит его как чужую
  ссылку (карты и ответ, без вопроса и заметки).
- `POST /api/account/claim` без токенов переносит **все** гостевые расклады куки этого устройства — на общем
  компьютере это и расклады предыдущего человека. Звать его один раз, сразу после входа, начатого явным действием
  («Сохранить в дневник» / «Войти»), а не при каждой загрузке страницы. Этап 4.4б (решение владельца 12): сайт
  шлёт `"device": true` только после входа, начатого на этом устройстве; ссылка из письма, открытая на другом
  устройстве, — `"device": false`, и переносится только расклад её токена.
- Текст политики конфиденциальности: после удаления аккаунта его номер хранится 8 дней в `deleted_accounts`,
  счётчик дня `user:<id>` — до 2 дней, `llm_calls` (номера и числа, без текстов) — 90 дней.
- Перед первой рассылкой Plus: гостевые заявки не подтверждены (любой может вписать любой адрес, 5 в сутки с
  адреса) — подтвердить письмом или писать только строкам с `user_id`.

## Счётчик событий (этап 4.4а)

Спецификация — `docs/superpowers/specs/2026-11-19-stage4-4a-reading-screens-design.md`, §6. Сайт шлёт
`POST /api/events {"name", "tool", "lang", "params"}` через `navigator.sendBeacon`; ответ — `204` без тела. Принимаются
только события и параметры из `docs/design/analytics-events.md` (`app/events.py`, каждый параметр события обязателен,
лишний — `422 {"reason": "invalid", "fields": ["params.<имя>"]}`). Ни адреса, ни cookie, ни номера гостя или аккаунта
не пишется: таблица `events` (миграции 004, 007) — день UTC, имя, инструмент, язык, параметры, время. Миграция 007 (этап 4.4б,
`remind_click`) пересоздаёт ограничение имени: перед выкладкой проверить его имя на живой базе —
`SELECT conname FROM pg_constraint WHERE conrelid = 'events'::regclass AND contype = 'c';` — ожидается
`events_name_check` (иначе миграция остановится на `DROP CONSTRAINT`, ничего не изменив: она идёт одной транзакцией). Больше
`EVENTS_PER_MINUTE` (30) запросов в минуту с адреса или `EVENTS_GLOBAL_PER_MINUTE` (600) со всех адресов вместе —
`429 {"reason": "rate"}`, ничего не пишется (счётчики в памяти, как у всплеска раскладов).

Воронка `tool_view → draw_click → reading_shown → save_click` по инструментам и языкам за период (разбор — через
2–3 недели после запуска); `signup_done` без инструмента считается отдельно. Запрос берёт строки только с дня запуска
(14.12.2026; сдвинется запуск — поправить дату): события закрытого стенда — проверки, а не посетители.

```sql
SELECT tool, lang,
       count(*) FILTER (WHERE name = 'tool_view')     AS views,
       count(*) FILTER (WHERE name = 'draw_click')    AS draws,
       count(*) FILTER (WHERE name = 'reading_shown') AS shown,
       count(*) FILTER (WHERE name = 'save_click')    AS saves,
       round(100.0 * count(*) FILTER (WHERE name = 'reading_shown')
             / nullif(count(*) FILTER (WHERE name = 'draw_click'), 0), 1) AS shown_pct
FROM events
WHERE day >= DATE '2026-12-14' AND day BETWEEN %(day_from)s AND %(day_to)s AND tool IS NOT NULL
GROUP BY tool, lang
ORDER BY tool, lang;
```

В SQL Editor Supabase вместо `%(day_from)s` и `%(day_to)s` подставить даты, например `'2026-12-14'` и `'2027-01-04'`.

потолка `--max-usd N` не запускается (оценка выше потолка — тоже отказ); все вызовы идут через `evals/metering.py`,

кодом 4, а потраченное печатается и пишется в отчёт (`spent_usd`, `not_done`); потолок можно превысить не больше
чем на один вызов. Коды выхода `evals.run`: 0 — прогон прошёл; 1 — прогон не прошёл (FAIL в отчёте); 2 — не
запускался и ничего не вызвано (нет `--yes` или `--max-usd`, оценка выше потолка, у модели нет цены); 3 — пустой ключ;
4 — остановлен потолком (`not_done` в отчёте). `--yes` — только после «да» владельца, ключ — из `deploy/.env`
(`set -a && . deploy/.env && set +a`); пустой ключ останавливает прогон до первого вызова. Результаты —
`api/evals/results/` (в git не попадают).
