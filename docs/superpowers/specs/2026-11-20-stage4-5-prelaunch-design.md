# Подэтап 4.5: доработка до запуска — дизайн

Дата: 20.11.2026. Основа: проход по стенду 20.11.2026 (`.superpowers/sdd/progress-s44a.md`, находка F1), итоговая
проверка 4.4а Fable 5.2 (`.superpowers/sdd/s44a-final-review.md`, решение владельца 3), спецификация 4.4а §11.1

строка «3 cards — the majority decides, and you see what tips it»), `docs/design/00-design.md` решение 7 (при трёх

## 1. Цель и рамки

До запуска 14.12.2026 закрыть три вещи, которые видит посетитель:

1. **Сначала помощь, потом лимит.** Тревожный вопрос получает кризисный ответ, даже если расклады на сегодня
   закончились или уточнения исчерпаны.
2. **«Да/нет» на три карты** — переключатель «1 карта / 3 карты» на `/yes-no` и `/es/si-o-no`.
3. **Один запрос — один расклад.** Повтор запроса после обрыва связи не списывает второй расклад и не создаёт
   второе уточнение.

Вне рамок: 4.4б (сохранение, вход, дневник, аккаунт), справочник «да/нет» по картам (этап 6), тексты этапа 5.

## 2. Решения владельца (20.11.2026)

1. Сначала доработка сервера, потом 4.4б.
2. Кризисная проверка — до лимита, до запуска (находка прохода F1).
3. «Один запрос — один расклад» — до запуска, вместе с «да/нет» на три карты.
4. Ответ «да/нет» на три карты: **под каждой картой её голос** («Да» / «Нет» / «Пока неясно»), ниже крупно итог и
   «почему».
5. Платный прогон тестового набора — только после отдельного «да» владельца с названной суммой (ожидаемо ≈ $1).

## 3. Сначала помощь, потом лимит

**Расклад** (`POST /api/readings`), новый порядок:

1. Защита от злоупотреблений — как сейчас и первой: дневной предел адреса (`429 ip_limit`), Cloudflare Turnstile.
2. **Проверка вопроса** (стоп-фразы, затем модель проверки в пределах её бюджета `GUARD_BUDGET_USD` и лимита
   проверок на адрес): кризис → `200` кризисный ответ (`remaining` как сейчас), расклад не тратится, слот не
   занимается. Пустой вопрос не проверяется.
3. Только потом лимит дня (`429 limit`) и создание расклада.

Вопрос, проверенный на шаге 2 и не кризисный, на шаге 3 проверяется заново не должен: результат проверки
используется при создании расклада (как сейчас `guard_group`, `guard_source`).

**Уточнение** (`POST /api/readings/{id}/followups`), новый порядок: защита адреса → **проверка вопроса** (кризис →
`200` кризисный ответ, как сейчас, попытка не тратится) → `429 attempts` → `402 confirm` / `402 plus` → создание.
Проверка модели при этом тратит слот проверки адреса, как сейчас.

Стоимость: человек у лимита, задающий обычные вопросы, тратит проверку модели на каждый отказ. Это ограничено уже
действующим пределом проверок на адрес и суточным бюджетом проверки; сверх бюджета работают только стоп-фразы
(как сейчас).

## 4. «Да/нет» на три карты

**API.**
- `POST /api/readings` с `kind: "yes_no"` принимает `count: 1 | 3` (по умолчанию 1; для других видов поле
  запрещено — `422`). Три карты стоят **один** расклад, как `three`.
- Позиции трёх карт «да/нет» — без времени: `card` у каждой (не прошлое/настоящее/путь). В ответе API у каждой
  карты — её голос `vote: "yes" | "no" | "unclear"` (правило `card_verdict` из `app/cards.py`: база карты,
  перевёрнутая → «пока неясно»); итог `verdict` — большинством (`spread_verdict`, уже есть: два из трёх, иначе
  `unclear`).
- Вопросы без вердикта (здоровье, смерть, суд, безопасность, другой человек — §8.1 спецификации 4.2) остаются
  без итога и без голосов и при трёх картах.
- Число карт в базе не ограничено (`cards jsonb`), миграция для этого не нужна; меняется `KIND_COUNTS` /
  `positions` в `app/draw.py` (число карт `yes_no` — из `count`).

**Чтец.**
- Промпт v6 (EN/ES) для `yes_no` с тремя картами: заголовок с итогом; разделы `card1`–`card3` — по абзацу на
  карту с её голосом; `synthesis` — что склонило итог (или почему большинства нет); `step` — один шаг; `why` — одна
  строка «почему». Проверки ответа (`finalize.py`) — как для `yes_no` сейчас.
- Ответ из базы значений (модель недоступна) собирается и для трёх карт: голос и `yes_no_why` каждой карты, итог.
- Уточнения к такому раскладу — как к любому.

**Тестовый набор.** В `api/evals/questions.<lang>.jsonl` — по 10 вопросов «да/нет» на три карты на язык (включая
вопросы без вердикта и с ничьей). Прогон с судьёй — платный, только после «да» владельца с суммой; порог — как в
4.2.

**Сайт.**
- `/yes-no`, `/es/si-o-no`: переключатель «1 card / 3 cards» («1 carta / 3 cartas») и подсказка под ним — тексты
  прототипа (`YesNo`); по умолчанию одна карта; кнопка — «Draw a card» / «Draw three cards» по выбору.
- Ночная комната: под каждой из трёх карт — её голос (иконка и слово, `VerdictIcon` из 4.4а), ниже крупно итог и
  «почему»; на компьютере — две колонки, как у расклада на три карты.
- Аналитика: `cards_revealed` с `cards_count: 3`; инструмент — `yes_no`.
- Из спецификации 4.4а убирается отметка «без переключателя» (§3, §11.1).

## 5. Один запрос — один расклад

**Сайт.** На каждое нажатие «Вытянуть» и на каждое отправленное уточнение сайт создаёт номер запроса
`request_id` (UUID v4) и шлёт его в теле. Тот же номер — при повторе того же нажатия: если `POST` не получил
никакого ответа (обрыв, тайм-аут), сайт один раз сам повторяет запрос с тем же номером, затем показывает обычное
восстановление. Новый номер — только на новое нажатие.

**API.**
- `POST /api/readings`: если у этого владельца (аккаунт, иначе гость устройства) уже есть расклад с этим
  `request_id`, API возвращает его (`201`, тот же вид и `remaining`), слот не занимается, проверка вопроса не
  повторяется. Номер чужого владельца не находит ничего (создаётся новый расклад).
- `POST /api/readings/{id}/followups`: уточнение с тем же `request_id` в этом раскладе → поток этого уточнения
  (ответ уже записан — его повтор; пишется — как сейчас при повторном подключении), попытка и расклад не
  тратятся второй раз.
- `request_id` необязателен (старые вкладки без него работают как сейчас).
- Номер уточнения `n` больше не повторяется: берётся из счётчика попыток расклада (`followup_attempts`), а не как
  максимум существующих + 1. Это закрывает случай «другая вкладка во время восстановления» (Fable, R1/M1
  финальной проверки 4.4а).

**Миграция 005.** `readings.request_id uuid` + уникальность в пределах владельца; `followups.request_id uuid` +
`UNIQUE (reading_id, request_id)`. Только добавление столбцов и индексов — безопасно на живой базе.

## 6. Проверки

- Тесты API: порядок «кризис раньше лимита» для расклада и уточнения (кризис у лимита → кризисный ответ; обычный
  вопрос у лимита → `429`; кризис у исчерпанных попыток и при `402` → кризисный ответ); `count` и голоса;
  повтор `request_id` (тот же расклад, слот один; чужой владелец; уточнение); `n` не повторяется.
- Тесты сайта (Vitest): переключатель и тело запроса, голоса в ночной комнате, повтор с тем же номером, один
  автоматический повтор.
- Платный прогон тестового набора — после «да» владельца.
- Проверка плана и итоговая проверка ветки — Fable 5.2; выкладка; короткий проход по стенду: кризис после лимита,
  «да/нет» на три карты (EN и ES), обрыв при создании расклада.

## 7. Что делает владелец

1. «Да» на платный прогон тестового набора (сумма будет названа).
2. Решение о слиянии и выкладке.

## 8. Готово, когда

- Тесты зелёные; прогон тестового набора — не хуже порога 4.2; итоговая проверка Fable — «готово к слиянию».
- На стенде: тревожный вопрос у исчерпанного лимита получает помощь; «да/нет» на три карты показывает голоса и
  итог на обоих языках; повтор после обрыва не тратит второй расклад.
